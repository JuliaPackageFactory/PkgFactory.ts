## 公開前の設計判断

参考として挙げられた3点も検討し、今回は以下を採用します。

1. **切断で停止し、明示的に再開する。** これは合意済み仕様です。バックグラウンドで作成を完走させる変更は行いません。送信済みの結果不明な書込みを照合するジャーナルと接続監視を維持します。
2. **排他を単一のApplicationStateで確定する。** 異なる利用者が同じリポジトリへ書く競合と、全体8件の実行上限を同じ原子的更新で扱います。利用者間の更新でもCASが競合し得る点は受け入れ、再試行は20回で制限します。失敗したclaimからGitHub書込みへ進みません。AuthStateは索引と接続元制限を利用します。現時点の受入負荷を超える規模への容量保証はしません。
3. **回復マーカーと完了コミットを維持する。** サーバーが書込み応答を受け取れなかった場合にも、GitHubにあるplan ID・digest・Project.tomlハッシュから帰属と改変を確認できます。完了マーカーも再照会できるため、結果が不明なworkflow_dispatchを再送してCIを重複起動する必要がありません。

## 公開環境の攻撃対策（2026-09-30）

ステージングへの配備を前提に、想定される攻撃をコードと実行で確認し、次の対策を追加しました。

| 想定した攻撃 | 対策 | 検証 |
|---|---|---|
| 未認証の要求を大量に送り、OAuth KV・AuthStateへの書込みやGitHub呼出しで費用と負荷を増やす | KV・AuthStateへ書き込むかGitHubを呼ぶ匿名ルートを接続元ごとに合計毎分120回、動的登録を毎分10回に制限。サインイン後のWeb APIとMCPはGitHubアカウントごとに毎分120回 | workerdで同じ接続元の登録3件目とトークン要求7件目が429、`/auth/login` も同じ枠で429。別の接続元・別のアカウントは継続でき、`/health` は制限しない |
| 形式だけ正しい偽のセッションCookieで、全利用者共通のAuthStateを呼ばせる | セッションIDに `SESSION_KEY` から派生した鍵のHMAC署名を付け、署名が合わなければAuthStateへ問い合わせずに拒否 | 署名のないID、別IDの署名を付けたIDが401 |
| 悪意あるMCPクライアントがリモートのHTTPを戻り先にし、認可コードを平文で受け取る | 動的登録と認可開始の両方で、HTTPS・ループバックへのHTTP・カスタムスキーム以外を拒否。CIMDと既存登録にも適用 | HTTPSとリモートHTTPを混ぜた登録が400、HTTPSとカスタムスキームの登録は201。localhostに似た外部ドメインを拒否 |
| JSON-RPCバッチで `tools/call` を送り、切断監視を回避する | `/mcp` のバッチと不正なJSONをJSON-RPCエラー（-32600 / -32700）で拒否 | 実際に発行したMCPトークンで、バッチの `create_package` が400、GitHubへの要求0件 |
| `SESSION_KEY` 変更後に古いCookieで全ページが502になる | 復号できないセッションを未ログインとして扱う | 別の鍵で暗号化したセッションで、トップページが未ログイン表示、APIが401 |
| ログアウト後もGitHubトークンが有効なまま残る | ログアウト時にOAuth AppのAPIでトークンを失効。失敗してもサーバーのセッションは削除 | Basic認証、本文へのトークン配置、URLにトークンを含めないことを確認。404・422・リダイレクト・通信失敗でもログアウト完了 |
| ログにOAuth codeやクライアント入力が残る、または攻撃を検知できない | Workers Logsを有効にし、invocationログは無効、クエリ文字列は削除。イベント名・メソッド・パスと、OAuthエラーの固定コードだけを記録 | wranglerのdry-runで検証用・本番用の設定を検証 |
| 開発依存やGitHub Actionsの改ざん・既知脆弱性 | wrangler 4.143.1とminiflare 5.20260926.1-alphaへ更新。ActionsをコミットSHAへ固定し、Dependabotで更新を提案 | `npm audit` 0件 |

Workers Rate Limitingのカウンタは拠点ごとの概算です。一つの接続元による費用・負荷を抑える対策で、複数の接続元からの大規模な攻撃に対する容量保証ではありません。

この変更に含めない事項:

- GitHub OAuth Appの `Expire user access tokens` が両アプリで有効かの確認。GitHubの管理画面で行います（[DEPLOYMENT.md](DEPLOYMENT.md)）。
- MCPのgrantを失効したときのGitHubトークン失効。
- 生成リポジトリのテンプレートに含まれるActions（`julia-docdeploy`・`TagBot` など）のSHA固定。生成物の方針に関わるため別に判断します。
