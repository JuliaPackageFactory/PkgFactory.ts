## 公開前の設計判断

参考として挙げられた3点も検討し、今回は以下を採用します。

1. **切断で停止し、明示的に再開する。** これは合意済み仕様です。バックグラウンドで作成を完走させる変更は行いません。送信済みの結果不明な書込みを照合するジャーナルと接続監視を維持します。
2. **排他を単一のApplicationStateで確定する。** 異なる利用者が同じリポジトリへ書く競合と、全体8件の実行上限を同じ原子的更新で扱います。利用者間の更新でもCASが競合し得る点は受け入れ、再試行は20回で制限します。失敗したclaimからGitHub書込みへ進みません。AuthStateは索引と接続元制限を利用します。現時点の受入負荷を超える規模への容量保証はしません。
3. **回復マーカーと完了コミットを維持する。** サーバーが書込み応答を受け取れなかった場合にも、GitHubにあるplan ID・digest・Project.tomlハッシュから帰属と改変を確認できます。完了マーカーも再照会できるため、結果が不明なworkflow_dispatchを再送してCIを重複起動する必要がありません。
